# Root Cause Analysis — "Added/assigned tasks disappear after update"

**Date:** 2026-06-19  ·  **Author:** Claude (with Rich Miller)  ·  **Severity:** High (board not trustworthy) · **Data loss:** None

---

## 1. Summary

Users adding or re‑assigning tasks on the MRA Command Center dashboard saw their
changes **vanish after the next "update"** (e.g. Fleetio issue #986 *Hinge Failure*
reverting to *Unassigned*; a "Fit new skirts" task on Ferguson never appearing).

The dashboard only ever displays **`data.js`** — a read‑only snapshot generated by the
export pipeline. The live `data.js` was **frozen at `2026‑06‑18T14:53Z` (~26 h stale)**
because the export pipeline had stopped regenerating it. Every change still wrote
correctly to the **workbook** (the source of truth), but the board kept reloading the
same June‑18 snapshot, so nothing new appeared. Two dashboard issues made this worse
and harder to spot (detailed below).

**Bottom line: no data was lost or corrupted.** All edits are in the workbook and were
recoverable; the problem was a stale display + insufficient visibility of staleness.

## 4. Root cause

**Primary root cause:** The export pipeline (`Update-Auto.ps1` → `Export-Data.ps1` →
AzCopy push of `data.js`) **stopped running**, so `data.js` was never regenerated from
the workbook. The dashboard, which can only show `data.js`, therefore showed stale data
indefinitely.

**5 Whys:**
1. *Why did changes disappear?* The board only shows `data.js`, which didn't contain them.
2. *Why didn't `data.js` contain them?* `data.js` wasn't regenerated after the changes.
3. *Why wasn't it regenerated?* The export pipeline didn't run after 2026‑06‑18 14:53.
4. *Why didn't it run?* **(Open — to confirm with Rich)** The export is run **manually
   (right‑click on Rich's PC)** and/or via a scheduled task that did not fire — likely
   because it depends on Rich's machine being on, OneDrive being synced, and the job
   being triggered. Single point of failure.
5. *Why was the failure invisible for ~26 h?* The only staleness signal was a small amber
   "26h old" tag in the header — easy to miss. No alert, no loud banner, no monitoring.

---

## 5. Contributing factors (dashboard‑side)

These didn't *cause* the freeze but amplified the pain / masked it:

1. **Staleness was nearly invisible.** A frozen board looked like a dashboard bug rather
   than a dead pipeline. *(Fixed — loud banner, §6.)*
2. **Optimistic pending‑cache was over‑aggressive (regression, rev 4.46).** A change meant
   to fix a Fleetio "ghost" started dropping a just‑added task as soon as any export ran,
   instead of holding it until it actually landed. With a *dead* export this also meant
   added tasks could drop. *(Fixed/reverted — rev 4.51.)*
3. **Edits/assignments aren't held in the optimistic cache (only adds).** On a reload, the
   stale board "snapped back," visually reverting an assignment that *had* saved to the
   workbook — making it look like data loss. *(Design limitation; see §6 short‑term.)*
4. **Edit‑job "Notes" trap.** Typing a task into the Edit‑job *Notes* cell does nothing
   when the job has a structured task list (export ignores the notes cell). Separate bug,
   same "it didn't show" symptom. *(Fixed — rev 4.47: relabeled + warning + ➕ Add task.)*
5. **Single‑machine, manual, push‑based export.** The whole freshness of the board depends
   on one PC running a script and pushing via AzCopy — no redundancy, no heartbeat.

## 6. Corrective & preventive actions

### Short‑term (prevent recurrence)
| # | Action | Type | Owner |
|---|---|---|---|
| P1 | **Reliable scheduled export** — Windows Task Scheduler job running `Update-Auto.ps1` on a fixed interval (e.g. every 15 min), set to run whether or not Rich is logged in, **with a log file** and "run on failure → retry" | Automation | Rich + Claude |
| P2 | **Export writes a run log + last‑success timestamp** (e.g. `export-last-run.txt`) so a stall is diagnosable at a glance | Detection | Claude (Export‑Data.ps1) |

| P4 | **Daily automated workbook backup** — Power Automate flow copies the workbook each morning, date‑stamped, into *Backup Archive* (today's backups are manual/ad‑hoc) | Backup | Claude (flow) |

### Longer‑term (resilience)
| # | Action | Type |
|---|---|---|
| L1 | **Move the export off the single PC** — run it as a scheduled cloud job (Office Script + Power Automate, or an Azure Function) that reads the workbook and writes `data.js` directly to Azure. Removes the "PC must be on + manual run + AzCopy" single point of failure | Architecture |
| L2 | **Persist edits/assignments in the optimistic cache too** (not just adds), so a stale board never visually reverts a saved change | Dashboard |
| L3 | **Escalate the banner past 24 h** (e.g. full‑screen "DO NOT TRUST — data > 1 day old") | Dashboard |

## 7. Detection: how we'll catch this next time

- **In‑app:** loud banner at > 12 h (live now). Escalation at 24 h proposed (L3).
- **Out‑of‑band:** heartbeat flow emails Rich within ~1 h of the export stalling (P3) —
  this is the key control, because it doesn't depend on the failing component.
- **Diagnosable:** export run‑log + last‑success file (P2).
